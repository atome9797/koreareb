# 코드 리뷰 & 대용량 조회 성능 개선

대상: `atome9797/koreareb` (Unity 2021.3 + SQLite + Python 위험도 산출)
범위: DB 접근 계층 전체, 실시·등록 화면, 로그인/비밀번호, 파이썬 업로드 스크립트, DB 스키마(인덱스)

---

## 0. 가장 먼저 할 일 — 개인정보

이 레포는 **public** 인데 아래 파일에 성명·생년·전화번호·주소·IP 컬럼이 마스킹 없이 들어 있다.

| 파일 | 내용 |
|---|---|
| `Assets/StreamingAssets/koreareb.db` | `tb_riskdata` 66,463행 (성명 37,422개, 전화번호 66,273개, 주소 32,765개가 서로 다름) |
| `korea_rebs/*.csv`, `korea_rebs/final/*.csv`, `korea_rebs/Run/*.csv` 등 | 같은 형식의 원본/전처리/결과 CSV (약 300MB) |

실제 데이터라면:

1. 레포를 바로 **private** 로 바꾼다 (Settings → General → Danger Zone → Change visibility).
2. 파일을 지우는 커밋만으로는 히스토리에 남는다. `git filter-repo` 나 BFG 로 히스토리에서 제거하고 강제 푸시한다. 포크/클론이 있었다면 그쪽 사본은 따로 지워야 한다.
3. 소속 기관의 개인정보 담당자와 노출 기간·범위를 공유한다.
4. 앞으로는 `*.db`, `*.csv` 원본 데이터를 커밋하지 않고, 개발용으로는 가짜 데이터 DB 를 따로 만든다.

이번 작업은 이 문제를 키우지 않도록 **DB 파일(`.db`)을 다시 커밋하지 않고**, DB 변경은 앱이 시작할 때 적용되는 마이그레이션 코드로 넣었다.

## 2. 느려지는 원인

### DB / SQL

1. **인덱스가 하나도 없음** (PK, `data_no` UNIQUE 제외). 모든 조회가 175개 컬럼짜리 `tb_riskdata` 전체(60MB)를 읽는다. 대시보드 한 번 여는 데 이런 쿼리가 7번.
2. **`SELECT *` 서브쿼리 + 윈도 함수**: `ROW_NUMBER() OVER(...)`, `COUNT(*) OVER()` 를 175개 컬럼짜리 행 그대로 정렬한다. 서브쿼리 안의 `ORDER BY` 로 같은 행을 또 정렬한다. 실시·등록 7초의 대부분이 넓은 행 정렬이다.
3. **지역 코드 계산이 인덱스를 못 탐**: 17줄짜리 `CASE apt_sup_pos/1000 ...` 를 서브쿼리에서 계산한 뒤 바깥에서 거른다.
4. 같은 테이블을 같은 기준으로 **4번 정렬** (대시보드 상위 5/10/20%/전체 평균).
5. 조회할 때마다 **연결을 새로 열고 닫음** → 스키마 재해석, 페이지 캐시가 매번 비워짐.

### 앱 (C#)

6. 실시·등록이 **214개 컬럼 × 전체 행**을 DataTable 로 받는다 (6.6만 건이면 약 1,400만 셀).
7. 받은 테이블을 `CheckTable.Copy()` 로 한 벌 더, **페이지를 넘길 때마다** `DefaultView.ToTable()` 로 또 한 벌. 메모리가 2~3배로 늘고 GC 가 자주 멈춘다.
8. **체크박스 클릭마다** `resultTable.Select("data_no = '...'")`, `Select("isSelect = True")` ×2 → 전체 행 검색 3번. `getCount()` 는 페이지 이동마다 전체 검색 3번.
9. 파일과 DB 결과 매칭에서 **DB 행마다 `OpenTable.Select(...)`** → 행 수의 제곱. 1.6만 × 1.6만이면 수억 번 비교.
10. 쓰기: **행마다** 연결 열기 → `SELECT COUNT` → `UPDATE/INSERT` → 커밋(디스크 동기화) → 닫기 + `await Task.Delay(1)`. 컬럼마다 `Debug.Log` 까지 해서 1.6만 행이면 로그만 수백만 번.
11. 대부분의 조회가 **메인 스레드에서 동기 실행** → 그동안 화면이 멈춘다 ("완성도가 떨어지는" 직접적인 원인).

## 3. 해결 방법 (적용한 것)

| # | 방법 | 효과 | 위치 |
|---|---|---|---|
| 1 | **커버링 인덱스**: 쿼리가 쓰는 컬럼(약 17개)을 모두 담은 인덱스. SQLite 가 175컬럼짜리 원본 행 대신 인덱스만 읽는다 (`USING COVERING INDEX`). 날짜를 맨 앞에 둬서 기간 조건으로 바로 범위를 자른다. | 읽는 양 1/5~1/10 | `Sql/migrations/001_performance_indexes.sql`, `DbMigrator.cs` |
| 2 | **좁게 먼저, 넓게 나중에**: `(data_idx, 위험도)` 두 컬럼만 뽑아 순위를 매기고 상위 %를 자른 다음, 남은 행만 rowid 로 원본에서 읽는다. | 정렬 대상이 1KB 행 → 16바이트 | `DatabaseAccess.SqlExecuteRankedCte`, `SqlMarketByDanji` |
| 3 | **필요한 컬럼만**: 실시·등록 화면이 실제로 읽는 47개 컬럼만 가져온다. 엑셀/파이썬 저장처럼 전체 컬럼이 필요한 경우는 DB 에서 한 행씩 읽어 파일로 바로 쓴다(스트리밍). | 메모리·로딩 1/4 이하 | `GetExecuteList`, `ExportRiskRowsToCsv` |
| 4 | **서버 페이징 API**: 순위는 DB 가 매기고 `LIMIT/OFFSET` 이후의 행만 넓은 테이블에서 읽는다. 개수는 따로 집계. | 페이지당 0.1~0.2초, 메모리 일정 | `GetExecutePage`, `GetExecuteCounts` |
| 5 | **한 번에 집계**: 퍼센트 4종을 정렬 1번 + 누적 평균으로. 지역 필터는 `IN (@c0, …)` 파라미터로 바꾸고 필터를 집계 전에 건다. | 2.5초 → 0.1초 | `SqlMapByDangerPercent` 등 |
| 6 | **배치 쓰기**: 트랜잭션 1개 + 재사용 커맨드(준비된 문장)에 값만 바꿔 실행. | 수천 배 (커밋 1번) | `DeleteByKeys`, `InsertRows`, `SaveExecuteResults` |
| 7 | **연결 1개 재사용 + lock + 백그라운드 실행**: 무거운 조회/쓰기는 `Task.Run` 에서. lock 은 동기 코드 안에서만 잡아 메인 스레드와 교착이 생기지 않게 했다. 화면이 호출 직후 다시 쓰는 선택 배열(지역/모델/상위 %)은 호출 시점에 복사해서 넘기고, 이미 열린 연결은 lock 없이 꺼내 백그라운드 작업 중에도 메인 스레드가 기다리지 않는다. | 화면 멈춤 제거 | `ServerManager` |
| 8 | **화면 캐시**: 복사본 대신 참조, `data_no → 행` 사전, 선택 행 집합, 정렬/필터 결과 배열을 바뀔 때만 다시 계산. | 클릭/페이지 이동이 행 수와 무관 | `ViewExecute` |
| 9 | **WAL + busy_timeout**: 읽기와 쓰기가 서로 막지 않고, 파이썬 스크립트가 쓰는 중이어도 바로 'database is locked' 로 실패하지 않는다. `cache_size` 64MB, 임시 데이터는 메모리. | 동시성·안정성 | `DatabaseAccess.OpenDatabase`, `DbMigrator` |

결과가 이전과 같은지는 `Sql/tools/verify_queries.py` 로 확인한다 (6장).

## 4. DB 변경 (마이그레이션)

- `DbMigrator.cs` 가 앱 시작 시 `PRAGMA user_version` 을 보고 아직 적용하지 않은 변경만 트랜잭션 안에서 적용한다. 여러 번 실행해도 한 번만 적용된다.
- 001: 커버링 인덱스 2개(모집공고일 기준, 업로드일시 기준), 지역 코드/로그 날짜/회원 아이디 인덱스, `ANALYZE`. 이후 WAL 모드 전환.
- 같은 내용을 `Sql/migrations/001_performance_indexes.sql` 에 두었다. DB Browser 에서 확인하거나 수동 적용할 때 쓴다. **둘을 같이 고쳐야 한다** (verify_queries.py 가 둘이 같은지 검사한다).
- 테이블 구조(컬럼)는 바꾸지 않았다. 엑셀/저장 코드가 컬럼 **위치**에 의존하고(`korcolname` 172개), 파이썬 스크립트도 같은 테이블을 쓰기 때문.
- 최초 실행 때 인덱스 생성에 6.6만 행 기준 약 0.5초, 66만 행 기준 약 5초 걸린다. 콘솔에 `[DB] migration 1 applied (… ms)` 가 찍힌다.
- WAL 모드에서는 실행 중에 `koreareb.db-wal`, `koreareb.db-shm` 파일이 생긴다. 앱이 정상 종료하면 합쳐지고 사라진다. `.gitignore` 에 추가했다. 앱 실행 중에 `.db` 파일만 복사하면 최근 변경이 빠질 수 있으니 앱을 끄고 복사할 것.
- **에디터에서 처음 실행하면 저장소의 `Assets/StreamingAssets/koreareb.db` 자체가 바뀐다** (인덱스·`user_version`·WAL 설정이 들어가 60.5MB → 75MB). git 에 변경으로 보이지만 개인정보 DB 이므로 커밋하지 말 것 (0장).
- 결과 저장은 `change_date` 를 바꾸지 않는다. `change_date` 는 '업로드일시' 이고 대시보드의 '최근 업로드일 기준 1년' 을 정하기 때문에, 점검 결과를 저장할 때마다 바뀌면 저장하지 않은 신청자가 대시보드에서 빠진다. 업로드(`SendInsertUpdate.py`)는 이전처럼 올린 시각으로 바꾼다.
